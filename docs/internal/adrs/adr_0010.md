# 10. Represent higher-kinded trait parameters as kinded constructor applications

Date: 2026-09-03

## Status

Proposed. Supersedes ADR 0009 when accepted.

## Context

Noolang currently parses `f a` in a trait signature as a lowercase nominal
`VariantType`. The typer later reconstructs facts that representation does not carry:
constructor identity and arity, modeled argument positions, preserved arguments, and
canonical `List` shape. ADR 0009 and parked PR #194 make that reconstruction bounded
and explicit with implementation-head slot descriptors, but each inference and module
path still has to preserve descriptor state.

Draft PR #195 tested the alternative selected by the kinded-constructor spike. Its
report, `docs/internal/research/kinded-constructor-calculus-spike.md` at commit
`a3b7e3f`, contains the algorithms, behavioral matrix, code measurements, and exact
inference probes. The revised spike passed local, wrapped, partial, imported,
non-leading, multi-argument, and shared-free-variable cases while deleting the four
legacy mechanisms identified by the spike gate. This supports changing the
representation rather than extending reconstruction metadata.

## Decision

Represent a trait constructor parameter and its application distinctly from ordinary
type variables and nominal value types:

- kinds are `Type` and monomorphic arrows between kinds;
- a constructor variable has a fixed kind derived from its uses in the trait;
- type application is an explicit type node;
- nominal constructors retain nominal identity and declared arity; and
- an implementation supplies an explicit compile-time constructor abstraction that
  beta-reduces to one saturated nominal constructor before ordinary unification.

Constructor abstractions are explicit, not inferred. Initially each parameter ranges
over `Type`, occurs exactly once as a direct argument of the resulting nominal
constructor, and cannot escape as a runtime value. The direct, linear restrictions may
be relaxed by a later decision with motivating evidence; they are not claims about the
limits of the calculus. Selecting an implementation remains nominal and coherent by
`(trait, constructor)`; kinds and beta reduction do not change runtime dispatch
identity.

Production must use this representation end to end. It must remove, not preserve under
new names:

- lowercase fake-variant detection;
- trait/slot metadata attached to variants;
- positional append/slice reconstruction; and
- trait-specific synthetic-`List` normalization.

The implementation may not introduce a parallel descriptor or reconstruction channel.
Local and imported calls must carry the same constructor abstraction on the existing
nominal implementation registry entry.

## Surface syntax

Constructor abstractions use `typefn` at implementation heads:

```noo
implement Functor (typefn value => Result value error) (...)
```

`typefn` distinguishes erased compile-time abstraction from runtime `fn`. Abstractions
are implementation-local initially; this decision does not add named or reusable type
functions. Multiple parameters are written in source order before `=>`.

## Production acceptance consequences

A production implementation is accepted only when:

1. trait constructor uses are kind-checked consistently and malformed abstractions fail
   at declaration;
2. implementation members are checked against a rigidly instantiated, beta-reduced
   trait signature, preserving universal-variable independence and effect subsumption;
3. PR #194's positive and negative behavioral matrix passes with exact inferred
   argument order for direct calls, wrappers, partial application, fixed/free and
   modeled arguments, and module transport;
4. ordinary value traits, conditional instances, primitives, and canonical `List`
   behavior remain unchanged;
5. the four legacy mechanisms above are absent from production code; and
6. the temporary nested-match rewrite of `Applicative Option::apply` is removed: its
   direct `Some g => map g opt` form must type-check through member compatibility and
   the common constructor-application path, without descriptor or reconstruction
   state.

Passing focused tests is insufficient. Full tests, stdlib-as-import tests, typecheck,
document validation, and exact manual `--types` probes are required because this area
has previously gone green with wrong inferred types.

## Excluded territory

This decision does not add general higher-kinded inference, higher-order unification,
kind polymorphism, higher-rank types, reusable constructor composition, type-level
computation beyond explicit beta reduction, overlapping instances, runtime type-lambda
values, or an effects redesign. A need for any of these is new design evidence, not
permission to broaden this implementation.

Erased aliases and structural types remain ineligible for instance identity. This does
not restrict structural typing or duck typing generally: those values only lack the
nominal runtime tag needed to select an implementation. Diagnostics must say so and
point to a nominal variant or the alias's underlying nominal type. Giving aliases
independent identity requires a separate nominal/newtype decision.

## Rejected alternatives

- **ADR 0009 / PR #194 slot descriptors:** behaviorally credible and still the fallback,
  but they preserve a second representation of constructor application and require its
  metadata to survive substitution and module transport. The spike demonstrated a
  smaller conceptual state space without it. Keep PR #194 parked until this replacement
  passes production acceptance; return to it if implementation requires parallel
  descriptor state.
- **Infer leading or positional slots:** cannot express non-leading modeled arguments
  and already produced passing-but-wrong types.
- **Add kind or lambda syntax over the existing fake variants:** adds a layer while
  retaining the reconstruction paths this decision is intended to delete.
- **Infer arbitrary type-level functions:** unnecessary for current traits and requires
  higher-order inference outside the demonstrated boundary.
- **Ship the spike directly:** it does not perform rigid implementation-member
  checking and remains research code despite validating the representation.

## Migration

Migration is intentionally atomic for constructor-valued traits:

- change the type AST, parser lowering, substitution, unification, freshening,
  generalization, display, and all other type traversals to recognize constructor
  variables and applications;
- require explicit abstractions for higher-kinded implementation heads and migrate the
  stdlib instances together;
- reject old constructor-valued heads with a focused migration error rather than a
  positional compatibility mode;
- keep value-valued implementation heads and nominal registry/manifest keys unchanged;
  and
- migrate tests, examples, and documentation in the same pass.

This migration touches more generic type traversals than ADR 0009, but removes the
trait-specific recovery paths. If production work cannot keep that invariant, stop and
reconsider the parked descriptor approach rather than layering both models.
