# 8. Tail-position trampolining, not CPS or a bytecode VM, for TCO

Date: 2026-08-30

## Status

Accepted, implemented (`src/evaluator/evaluator.ts`:
`evaluateTailPosition`, `runTrampolined`; `FunctionValue.tailInfo` in
`evaluator-utils.ts`).

## Context

The evaluator is tree-walking; a noolang function call is a JS call
(`evaluateExpression` → `evaluateApplication` → closure `.fn(arg)` →
`evaluateExpression(body)` → ...). Self-tail-recursive call chains
overflowed the JS stack at ~10,000-11,000 depth (measured, `bun test`
v1.3.14, in-process). Hit in practice: `std/parser.noo`'s `many`-based
combinators and `std/json.noo`'s string parser (worked around in PR #188
with a `reduce`-based scanner instead of the idiomatic combinator form —
see `docs/internal/ideas/TAIL_CALL_OPTIMIZATION.md`, PR #189).

Three strategic options were considered: (A) a targeted trampoline —
detect tail calls into same-owner closures at the evaluator's application
site and bounce through a loop instead of recursing; (B) rewrite the
evaluator in continuation-passing style so every call becomes a JS tail
call, uniformly trampolined; (C) compile to bytecode with an explicit
call/operand stack, no JS recursion at all.

B and C both replace execution semantics for effects tracking, trait
dispatch, and closures — a second interpreter, not a fix to this one. C is
filed separately as a not-started idea
(`docs/internal/ideas/BYTECODE_VM_REWRITE.md`) for if/when actual
performance or debugging-tooling needs justify that scope. Neither was
needed to solve the problem that was actually hit: self/mutual tail
recursion overflowing on ordinary control flow.

## Decision

Option A. `evaluateTailPosition` is a syntactic tail-position dispatcher —
plain JS recursion through node kinds that preserve tail position (`if`,
`match`, `where`'s main expression, `;`, single-step `pipeline`,
`typed`/`constrained` wrappers), bounded by a function body's *static*
nesting depth, not by call count. At `application`, a saturated call into a
same-owner terminal closure (`FunctionValue.tailInfo`, attached only to the
two closures `createCurriedFunction` creates that actually evaluate a
function body) returns a `TailCall` marker instead of invoking `.fn`.
`runTrampolined` loops on that marker inside one JS frame per logical call,
not per bounce.

**Syntactic, not semantic TCO.** `$`, `|` (thrush), and the evaluated
branch of `&&`/`||` are real tail positions too but are explicitly out of
scope — a deliberate, reviewable boundary, not an oversight. Same-shape
follow-up if they turn out to matter.

**Owner-gated, not universal.** Each imported module gets its own
`Evaluator` instance (`src/module-loader.ts`). A tail call into a
closure owned by a *different* evaluator always falls through to a normal
`.fn` call rather than fusing the loop across instances — bouncing there
would run the callee's body under the caller's trait registry,
`environment`, and `currentFileDir`, corrupting relative-import resolution
and trait dispatch. The call itself still works; only cross-evaluator loop
fusion doesn't happen.

**Duplicated, not shared, dispatch logic.** `evaluateTailPosition` does not
call into `evaluateIf`/`evaluateMatch`/`evaluateWhere`/`evaluateApplication`
— each case instead re-implements the small amount of branch-selection/
pattern-matching/definition-installation/application logic it needs. This
was checked, not assumed: an earlier version extracted shared helpers
(`selectIfBranch`, `findMatchingCase`, `installWhereDefinitions`,
`applyArgToCallable`), and the one added JS stack frame per extraction was
enough on its own to overflow an already-borderline test
(`std/json.noo`'s long-string parse, ~6000 chars — the exact test this
work traces back to). All four extractions were reverted; duplication is
the accepted cost, not a shortcut.

## Consequences

- Self-tail-recursive noolang functions are stack-safe at effectively
  unbounded depth (verified to 500,000 calls in ~1.5s) instead of
  overflowing at ~10,000-11,000.
- Non-tail-recursive workloads: no measurable regression. `fib 27`
  (~832k calls, non-tail via `+`) benchmarked within noise before/after
  (~2000ms both), despite every terminal-closure call now routing through
  `runTrampolined`/`evaluateTailPosition` instead of `evaluateExpression`
  directly.
- `where`-scoped recursive bindings (self *or* mutual) remain broken,
  independent of this change — `evaluateWhere` never Cell-wraps its own
  definitions the way top-level `=` does. Not touched here; a genuine
  letrec-binding-group feature if wanted, filed separately if it comes up.
- True mutual recursion between top-level bindings (two `fn`s referencing
  each other directly) doesn't work in noolang today either — confirmed
  during test design, out of scope for the same reason.
- A future change to `evaluateIf`/`evaluateMatch`/`evaluateWhere`/
  `evaluateApplication` can silently drift out of sync with
  `evaluateTailPosition`'s mirrored logic; nothing enforces staying in
  sync beyond a same-file comment pointing each tail-position case at the
  non-tail method it mirrors.
