# 11. Derive `Eq` structurally for tuples, records, and variants

Date: 2026-09-04

## Status

Accepted.

## Context

`==` / `equals` resolves only through registered nominal `Eq` instances. Every
product and sum shape therefore needs a hand-written instance:

- `{1, "a"} == {1, "a"}` → `No implementation found for operator ==`
- a user `variant V = A Float String` has no `==` until the author writes one
- `stdlib.noo` only papers over this for `Option`, `Result`, `List` by writing
  the instances out

Tuples and records make it worse: ADR 0010 correctly bars a user `implement Eq
{a, b}` head (no nominal runtime tag, no coherence story for a structural
head), so their equality is not fixable in userland at all. `List {String,
JsonValue}` in `std/json.noo` is the live example — its `Eq JsonValue` walks
the object arm with `primitive_list_all2` because `xs == ys` has no tuple `Eq`
to recurse through.

The equality of a product or sum whose components are all `Eq` is canonical:
one structural definition, no competing instance possible, no reconstruction
metadata. That is the case worth deriving.

## Decision

Resolve `T implements Eq` structurally when `T` has no registered instance and
`T` is a tuple, record, or declared `variant`:

- **tuple** — satisfied iff every element type is `Eq`; equal iff same arity and
  all elements equal.
- **record** — satisfied iff every field type is `Eq`; equal iff same field set
  and all fields equal.
- **variant** — satisfied iff every constructor's payload types are all `Eq`;
  equal iff same constructor and all payloads equal.

Recursive: a component's own `Eq` is used, nominal or derived, so recursive
variants (`JsonValue`) and nested structures resolve.

Derivation is **automatic and implicit**. An explicit `implement Eq T`
suppresses it — coherence stays one definition per `(Eq, T)`. Derivation is a
resolver/evaluator capability, not a registry entry: it does not create a
structural `implement` head, and ADR 0010's `nominalImplementationTarget` guard
and its diagnostics are unchanged.

Scope is `Eq` only. `Ord` and `Show` want the same mechanism but each carries
its own convention question (constructor order for `Ord`, formatting for
`Show`) and is a separate decision.

## Rejected alternatives

- **Arity-keyed nominal-ish tuple instances (`tuple2`, `tuple3`, …):**
  contradicts ADR 0010, caps arity, and repeats N boilerplate instances per
  trait.
- **A `deriving` keyword:** tuples and records have no declaration site to hang
  it on, so they must be implicit regardless; adding syntax only for variants
  splits the model for no gain, since explicit `implement` already opts out.
- **Polymorphic runtime `==` that ignores instances (OCaml `=`):** breaks
  user-defined `Eq` (normalized keys, set/map types) and abandons coherence.
- **Leave it:** constant friction on every new shape, and structural shapes
  stay permanently unfixable.

## Consequences

Touch points:

- `constraint-resolution.ts` — `tryResolveConstraints` gains a structural
  satisfaction path for `Eq`; its local `getTypeName` currently returns `null`
  for tuple/record and must not short-circuit them.
- `trait-system.ts` `resolveTraitFunction` — a structural operand for `Eq` is
  no longer an immediate miss.
- `evaluator.ts` — the `==`/`!=` path (currently: nominal `equals` or throw
  `Cannot compare … for equality`) gains component-wise structural comparison,
  recursing through `equals` per component; arity, field-set, or constructor
  mismatch yields `False`, never an error.
- `stdlib.noo` — `Eq (Option a)` / `Eq (Result a b)` / `Eq (List a)` may stay
  (canonical, removing them is churn); derivation covers what they do not.
- `std/json.noo` — `implement Eq JsonValue` becomes derivable end to end
  (`JArray`/`JObject` arms included); the hand-written instance and the
  `primitive_list_all2` object walk can go.

Typing:

- `{1, "a"} == {1, 2}` stays a type error (element mismatch), not `False`.
- `A 1 == B 2` for one variant is well-typed and `False`.

Acceptance (this area has gone green with wrong inferred types before — ADR
0010): full `bun test`, `stdlib.test.noo` as import, `bun run typecheck`,
`node validate_examples.js`, and manual `NO_COLOR=1 bun src/cli.ts --types`
probes on derived `Eq` at tuple, record, recursive variant, and nested-mixed
cases. Focused tests alone are insufficient.

## Excluded

`Ord` / `Show` derivation, a `deriving` surface syntax, structural `implement`
heads (still rejected), and general user-trait deriving. Any of these is new
design evidence, not a licence to widen this one.
