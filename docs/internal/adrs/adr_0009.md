# 9. Higher-kinded trait slots must be named explicitly, not inferred positionally

Date: 2026-09-01

## Status

Proposed. Not designed in detail, not scheduled, not implemented.

## Context

Noolang's types carry no kind information — `VariableType` is `{kind,
name, constraints}`, `VariantType` is `{kind, name, args: Type[]}`
(`src/ast.ts`). A trait like `Monad m` treats `m` as an ordinary type
variable; nothing marks it as standing for a type *constructor*, let alone
records its arity. When `m` unifies against a concrete multi-arg variant
(`Result a b`), `tryUnifyConstrainedVariant` (`src/typer/unify.ts`) and its
substitution counterpart (`src/typer/substitute.ts`) resolve which
argument the trait models by position: the trait's own arg count is
assumed to be a leading prefix of the concrete type's args, and everything
past that prefix is carried through as "extra," always appended at the
end.

This was tightened, not introduced, while fixing a real bug on PR #191
(`3a925e7`): `bind`'s trait dispatch was silently truncating `Result`'s
arity, producing a loud, honest `Variant arity mismatch` error. The fix
made the common case (every trait instance in `stdlib.noo` today) work
correctly. It did not remove the positional assumption — it made the
assumption's blast radius smaller and quieter.

**The hazard:** every current instance (`Monad`/`Functor`/`Applicative`
over `Result`, `Option`, `List`) happens to model the *leading* slot. A
future instance modeling a non-leading slot — a `Const a b`-shaped
`Functor` mapping over `b`, say — would not error. It would silently
produce a type with arguments in the wrong position: a value that
typechecks and is wrong, not a crash. That is a strictly worse failure
mode than the one this PR fixed, and per this codebase's own stated
typer-hazard policy (AGENTS.md: "several passing-but-wrong inferences have
shipped and been caught by hand"), silent-wrong is the failure this
project explicitly tries hardest to avoid.

Haskell avoids this with a real kind system: `Monad m` requires `m :: * ->
*`, kind-checked at the class/instance declaration, before unification
ever runs. Noolang copied the surface pattern (trait-constrained
higher-kinded type variables) without copying the kind system underneath
it that makes the pattern sound.

## Decision (proposed, not yet built)

Don't build kind inference. Make the varying slot an explicit, declared
fact instead of an inferred one: `implement` sites for higher-kinded
traits name the slot via partial type application —

```
implement Monad (Result a) (...)
```

instead of today's `implement Monad Result (...)`. The `a` marks which
argument position `Monad` models; any other position is declared free and
untouched by the trait. The typer records `(Monad, Result) → slot 0` from
this one line and looks it up during substitution instead of computing it
by slicing argument lists and assuming a prefix.

No kind variables, no kind unification, no kind inference propagated
through the pipeline — one explicit annotation per `(Trait,
TypeConstructor)` pair, checked once at the `implement` declaration.

## Consequences

- Closes the hazard by construction: a non-leading-slot instance either
  states its slot correctly (handled correctly) or fails to parse/check at
  `implement` time (loud, at the one place a human is already looking),
  never silently.
- Every existing higher-kinded `implement` in `stdlib.noo` (`Monad`/
  `Functor`/`Applicative` over `Result`, `Option`, `List`) needs its
  declaration migrated to the applied-partial form — a real, visible
  one-time cost, not free.
- Touches the `implement` parser grammar and trait-registration/lookup
  path, not just `unify.ts`/`substitute.ts`.
- Not urgent: nothing in `stdlib.noo` exercises the gap today (checked —
  every current instance models the leading slot). Worth doing before the
  first non-leading-slot instance is written, not after it misbehaves.
