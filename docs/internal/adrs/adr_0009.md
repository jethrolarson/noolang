# 9. Higher-kinded trait slots must be named explicitly, not inferred positionally

Date: 2026-09-01

## Status

Proposed. Not implemented.

## Context

Noolang has no kind information. A trait such as `Functor f` uses `f` as a type
constructor (`f a`), but the AST and registry record it like an ordinary type
variable and do not record constructor arity.

The typer currently assumes the trait models a concrete constructor's leading
arguments and appends any remaining arguments during substitution. PR #191
stopped this from truncating `Result a b`, but retained that positional
assumption. Today's stdlib works because all its constructor-valued instances
model slot 0; an instance over slot 1 could infer a plausible type with arguments
in the wrong positions. Passing-but-wrong inference is the hazard to prevent.

## Decision

A constructor-valued trait implementation marks each modeled constructor
argument with `_` in the `implement` target:

```noo
implement Functor (Result _ error) (...)       # models Result slot 0
implement Functor (RightMap context _) (...)   # models RightMap slot 1
```

`_` means the corresponding argument of `f a` occupies that constructor slot.
Named lower-case arguments are free: they are inferred, may appear in `given`,
and are preserved when modeled slots change. Omitted trailing arguments are
anonymous free parameters, so `(Result _)` preserves an unnamed slot 1. A
non-leading modeled slot must be shown explicitly.

Concrete arguments are fixed and must match without changing. Nested fixed
applications require grouping so parsing does not depend on constructor
metadata:

```noo
implement Functor (Outer error _ (Option error)) (...)
```

Here `(Option error)` is one fixed outer argument; the ungrouped spelling has
additional outer arguments. Modeled holes are direct arguments, never nested.

The number of holes equals the arity at which the trait parameter is consistently
applied in its signatures. `Functor` uses `f a` and therefore requires one. For
each occurrence `f T0 T1`, application position 0 fills the first `_` and
position 1 the second: `implement BiFunctor (Foo _ _) (...)`. This is the
existing ordered meaning of type application, not an assumption about variable
names or constructor payload-field order. The holes do not bind source names in
the member body; its term parameters and patterns bind values whose types follow
from the member and variant declarations. A trait that mixes bare and
differently applied uses of its parameter is invalid.

This is distinct from an applied conditional value instance:

```noo
implement Eq (Result a b)
  given (a implements Eq) and (b implements Eq) (...)
```

`Eq` uses its parameter as a value, not an applied constructor. `a` and `b` are
free parameters, not modeled slots. Parentheses or partial application never
select a slot; `_` does.

Allowed instance identities are nominal `variant` types, intrinsic `List`, and
the arity-zero intrinsic primitives `Float` and `String`. Erased `type` aliases
and structural types are excluded because runtime dispatch and coherence cannot
distinguish them nominally. `List` has arity 1, is written `(List _)`, and remains
canonical `ListType`, not a synthetic variant.

An implementation records its constructor and each slot's modeled, free, or
fixed role. Substitution reconstructs arguments in constructor order from that
fact rather than inferring positions by slicing and appending argument lists.

Member checking must preserve the independence of universally quantified trait
and free-slot variables: an implementation cannot pass by collapsing distinct
variables. Thus a body that maps `RightMap` slot 1 is rejected under the wrong
head `(RightMap _ value)` at declaration. A member may perform fewer effects
than its trait signature declares, but not effects absent from that signature.

Coherence remains one implementation per `(trait, constructor)`. Fixed
arguments, variable names, and slot layouts do not create overlapping or
specialized instances.

## Rejected alternatives

- Infer a leading slot from `(Result a)` or bare `Result`: this neither expresses
  the non-leading case nor removes the silent positional hazard.
- Keep legacy leading-slot inference as a compatibility mode: unsafe instances
  could still register successfully.
- Add kind inference: substantially broader than recording the fact known at an
  implementation site.
- Dispatch overlapping instances by fixed arguments or slot layout: that changes
  current constructor-wide coherence and needs a separate design.
- Give erased aliases instance identity: they need newtype-like runtime identity
  first.

## Compatibility and migration

This is a targeted source incompatibility. In the same implementation change,
constructor-valued stdlib heads migrate to `(Option _)`, `(Result _ error)` (or
`(Result _)`), and `(List _)`. Old higher-kinded heads may parse for a focused
migration error but must not register through inferred leading slots.

Value-valued instances, including primitives and `Eq (Result a b)`, retain their
meaning.

## Consequences

Implementation affects the `implement` target AST, trait/constructor metadata,
registry and module transport, substitution/unification, member compatibility,
and stdlib declarations. The slot information must travel with the instance so
local and imported dispatch agree.

Type-level acceptance checks must show that `(Result _ error)` maps slot 0 while
preserving slot 1, `(RightMap context _)` maps slot 1 while preserving slot 0,
and the same slot-1 body is rejected under `(RightMap _ value)`. They must also
cover canonical `(Option _)`/`(List _)`, conditional `Eq (Result a b)`, and the
existing `Result` arity and lambda-wrapper regressions.
